# V2 evidence-led numeric rediscovery (V3 candidate-only)

## Purpose and immutable boundary

This read-only utility turns the pinned V2 Census source/page provenance into a work queue for re-reading independently verified V3 source bytes. It does not import historical numbers as V3 observations, update SQLite, alter the 93 x 51 Census, change research policies or publish MCDA results.

## Scientific method from V2, reused as hints only

1. Source- and Project-scoped evidence discovery: the original V2 resource_retrieval.py used BM25, prioritizing frozen physical pages and searching resource/composition/context separately. The V3 implementation queries the existing candidate_search.py FTS5 index, with fixed pages first, interleaved value/composition hits, and separate context pages. The candidate defaults are 24 and 32 pages.
2. Native source verification: V2 semantic_resource.py, resource_source.py and resource_table_layout.py checked table captions, Total rows, column headers, printed tokens, JORC classification, estimate date and cutoffs. This *remains subsequent work* in V3 DocumentCache and resource_extraction.py; the present search tool does not validate numeric values.
3. Scientific admission: require source SHA, Project/Deposit/Resource Scope, statement and edition, effective/publication date, JORC classification, cutoff analyte/unit, material and chemical denominator, original token, displayed precision and independently re-read original text. Reuse V3 normalization.py, semantics.py, comparability.py, Temporal Gate and fresh_observations.py.
4. Derived Census values: use census_science.py only when formally selected component observations and complete membership/interval checks satisfy an approved versioned derivation policy. The tool creates no formally admitted or derived values.

No source/Project association is inferred by title/name similarity, and matching a V2 displayed number is not enough to admit a candidate. Missing source SHA, unindexed text, invalid Project association, multi-source provenance and unavailable legacy physical pages receive distinct statuses. A text hit remains a search lead.

## Outputs

- legacy_value_leads.jsonl: numeric resource and individual oxide historical hints, same-SHA and Project status, ranked pages; all carry candidate_only=true and original_value_confirmed=false.
- source_project_work_queue.json: unique (source SHA-256, Project ID) work items aggregating suggested pages, target columns and old page hints, with formal_admission=false.
- legacy_value_recovery_receipt.json: exact V2 provenance checksum, current V3 index checksum, linked source manifest SHA, counts, classifications and result hashes.

All output directories must start empty. Existing research outputs are never overwritten.

## Reproduction in an exact-source V3 workspace

Run the following from AU_REE_V3. The pinned V2 ref must exist in ../AU_REE_V2_reference. The V3 source manifest and Content Store are generated by the approved acquisition workflow; these paths refer to the reported local workspace, not version-controlled raw assets.

    PYTHONPATH=src python - <<'PY_CODE'
    from pathlib import Path
    from au_ree_v3.candidate_search import build_candidate_index
    build_candidate_index(
        Path("work/research-yield/source-inputs/source_manifest.json"),
        Path("work/fresh/source-store"),
        Path("work/legacy-resource-rediscovery/index"),
    )
    PY_CODE

    python tools/recover_legacy_value_hints.py \
      --v2-root ../AU_REE_V2_reference \
      --index work/legacy-resource-rediscovery/index/candidate_text.sqlite \
      --out work/legacy-resource-rediscovery/leads

    python -m unittest discover -s tests -p test_recover_legacy_value_hints.py -v
