AU_REE 開發治理規範 v3.0

適用範圍： AU_REE_V2 → AU_REE_V3 遷移、後續程式開發、研究模型建構及 Codex 自動化開發。

核心原則

本專案採用科學正確性優先、風險分級、增益導向、模組化及漸進式開發。

開發工作的主要目標是增加可驗證的研究能力、提升可比較資料品質、降低維護成本，並維持科學成果的可重播性。

不得以資料尚未完整、個別來源缺失、歷史技術債或尚未完成人工判斷為理由，停止其他可獨立執行的工作。

工程規範不得被解釋為禁止合理的模組新增、演算法替換或架構重構。

⸻

1. 科學不變條件

1.1 原始資料與證據

* 保留來源 URL、來源 SHA-256、Project ID、Observation ID、原始值、量測單位、材料及化學基準、適用範圍、研究截日與版本資訊。
* 不得無證據覆寫正式觀測值或修改既有來源紀錄。
* 不得虛構觀測、混用不同量測基準或將模型預測視為實測結果。
* 來源缺失不得導致其他獨立、有效資料被撤銷。

1.2 研究結果與重播

* 正式結果變更必須保存輸入、規則、程式版本及差異紀錄。
* 歷史凍結成果不得因新來源或新演算法而自動改變。
* 新方法可以產生獨立的研究版本，經科學驗證後再成為正式結果。
* 不變的科學輸入與規則應產生等價的科學結果；允許非科學性執行紀錄存在差異。

⸻

2. 自動化與資料採納權限

2.1 允許自動執行

允許按照既有核准規則，自動完成：

* 公開來源發現、取得、核驗與快取。
* PDF、HTML、表格及文字解析。
* NLP 資訊擷取及實體連結。
* 單位與化學基準正規化。
* 有公式及適用條件的衍生值計算。
* 證據相容性檢查、正式選值及資料庫更新。
* GIS 指標計算、MCDA 分析及研究成果輸出。

符合既有採納規則的資料可以直接進入正式流程，不要求逐筆人工簽核。

2.2 不確定資料

資料須明確區分：

1. 原始來源與原始觀測。
2. 尚未核驗的候選資料。
3. 已驗證的觀測。
4. 符合正式研究採納規則的數值。
5. 衍生資料、影子結果及模型推估。

證據不足、存在衝突或超出現行規則適用範圍的資料，保留在候選或影子層。

只有無法由既有證據與核准規則解決、且確實涉及研究方法選擇的問題，才需要研究者判斷。

⸻

3. 工程架構與模組責任

3.1 模組化原則

系統應依功能及責任劃分，而非依開發階段或日期不斷增加模組。

主要責任包括：

* 來源取得與版本管理
* 文件解析與 NLP
* 觀測資料與證據管理
* 正規化與本體論
* 資料驗證與正式選值
* Census 與 GIS
* MCDA 與統計分析
* 研究實驗與機器學習
* 版本發布與歷史重播

同一功能應優先共用已存在的資料契約、函式或介面。

新增模組時，須明確說明其責任、輸入、輸出及與既有模組的關係。

3.2 降低程式耦合

* CLI 只負責指令處理與工作調度，不應直接承擔複雜科學判斷。
* 資料取得、證據驗證、研究選值及 MCDA 運算應具有明確界線。
* 避免跨模組直接呼叫對方的內部實作細節。
* 大型函式修改時，應評估是否拆分為可獨立測試的責任單元。
* 禁止為解決局部問題而持續增加不必要的條件分支。
* 應檢查循環依賴、重複邏輯及高複雜度函式。

允許新增合理模組、第三方函式庫與替代演算法，但需說明其必要性、維護風險及環境重建方法。

不以模組數量、程式行數或零新增依賴作為驗收標準。

⸻

4. 檔案命名與生命週期管理

4.1 命名規範

正式程式與設定檔應使用可識別其功能的名稱。

例如：

* source_recovery.py
* observation_validation.py
* resource_normalization.py
* mcda_sensitivity.py

原則上不得在正式功能模組中使用僅表示開發批次的名稱，例如：

* phase11_new.py
* phase16_fix.py
* test_final_v3.py
* temporary_update.py

Phase、日期與實驗代碼可以出現在歷史報告、版本化執行結果及封存目錄中。

不能單純以檔名推定程式已過期；應根據實際依賴與功能判斷。

4.2 新檔案建立前的檢查

新增程式檔案前應確認：

1. 現有模組是否已提供相同功能。
2. 是否可擴充既有介面。
3. 新模組是否具有獨立且長期存在的責任。
4. 是否會形成重複資料流程。
5. 是否增加不合理的模組耦合。

符合獨立責任的新增模組可以直接建立，不要求人工逐檔批准。

4.3 檔案生命週期

每個既有檔案可依功能與使用情況分類：

* KEEP：繼續使用。
* REFACTOR：保留功能並重構。
* MERGE：與其他模組整合。
* ARCHIVE：保留歷史研究價值，移出現行執行鏈。
* REMOVE：已確認可安全移除。

判定是否移除時，須檢查直接與動態引用、CLI、CI、測試、設定及研究重播相依。

不可變的原始證據、歷史發布成果和必要重播資訊必須保留；可透過固定 Git ref、封存產物庫及雜湊清冊保存，不要求所有歷史產物持續留在現行工作樹。

4.4 研究結果管理

* 正式程式與研究輸出分開保存。
* 臨時測試、效能紀錄及中間產物不得無限制累積於正式資料目錄。
* 每次正式研究發布必須具備明確版本與輸入清冊。
* latest 或 current 可作為便利索引，但不可代替不可變的研究版本。
* 歷史報告可封存，不需要一直增加到主 README。

⸻

5. 版本治理與 V2 → V3 遷移

5.1 正式版本主線

* V3 應建立明確的整合主線。
* 功能分支用於有限範圍的開發與驗證。
* 已完成且通過相應驗證的功能應整合至正式主線。
* 不應長期依賴多層未合併 PR 作為正式版本管理方式。
* 尚未通過驗證的研究實驗，可以保留於隔離分支。

每次正式版本應保存程式提交、研究設定、資料契約版本及驗證狀態。

5.2 V2 遷移規範

* 遷移前固定明確的 V2 commit 與研究成果版本。
* 保留 V2 的 Project ID、來源 SHA、重要觀測、科學規則及已驗證演算法。
* 不要求沿用 V2 的檔案配置及所有舊函式。
* 使用版本化遷移程序建立 V3 資料結構。
* 既有資料若無法完整遷移，須記錄受影響範圍與原因。
* 遷移後須以固定研究樣本比較 V2 與 V3 的科學結果。

V2 可作為歷史唯讀基準，不應要求 V3 永久承擔全部 V2 舊版程式的執行相容性。

⸻

6. 漸進式驗證與執行效率

6.1 風險分級

驗證範圍依實際修改風險決定。

風險	變更類型	基本驗證
低	文件、非科學性命名、局部工具調整	靜態與直接依賴檢查
中	模組重構、解析器與資料流調整	單元及相關整合測試
高	證據驗證、選值、研究方法或資料契約改變	整合測試與受影響的封存重播
最高	正式結果、研究母體、科學規則或發布契約改變	完整相關研究重播、差異審查及發布驗證

風險由修改內容與影響範圍決定，不能僅依修改的檔案數量判斷。

6.2 執行效率

* 優先使用受影響測試集合，避免每次修改都重跑完整資料庫。
* 允許經 SHA 與輸入版本核驗的中間結果快取。
* 重複驗證工作應整合或共用可核對的產物。
* 重播與效能測試須記錄資料範圍、硬體或執行環境、快取狀態及耗時。
* 效能改善不得犧牲科學正確性。

6.3 失敗處理

驗證失敗須明確分類：

* CODE_ERROR：程式或資料契約錯誤。
* SOURCE_UNAVAILABLE：來源不可取得。
* EVIDENCE_INSUFFICIENT：證據不足。
* SCIENTIFIC_CONFLICT：來源或科學條件衝突。
* REPLAY_ENVIRONMENT_MISMATCH：重播環境或版本不一致。
* HYPOTHESIS_NOT_SUPPORTED：研究假說未獲支持。

不得把來源不可得視為所有模組失敗，也不得將未執行的驗證記錄為通過。

⸻

7. 研究探索與模型發展

允許 NLP、ML、本體論、GIS、統計模型及 MCDA 演算法進行平行研究。

每項新方法應具備：

* 明確的研究問題與預期增益。
* 固定的測試樣本及基準方法。
* 可重播的資料、程式及設定。
* 適當的性能與科學評估指標。
* 對模型限制、不確定性及資料洩漏風險的檢查。

NLP 的驗收可比較抽取準確率、召回率及經驗證的新增觀測；本體論應量測真正增加的可比較欄位或專案組合；ML 必須區分合成測試與真實事件預測。

MCDA 權重、評分函式與比較方法的變更，必須保存原始假設、固定輸入與敏感度結果。

允許負結果與零增益結果。若新方法尚未通過正式研究門檻，應留在實驗層，而非直接修改正式資料。

⸻

8. 每輪開發目標與驗收

每輪開始前須設定一個主要、可量測的目標，並明確界定基準版本及可獨立完成的工作。

完成後須回報：

1. 研究能力：新增哪些資料處理、驗證或分析能力。
2. 科學增益：與基準相比增加多少可驗證觀測、可比較資料、有效樣本或研究解釋力。
3. 工程變化：模組依賴、複雜度、重複實作及維護成本如何改變。
4. 執行成本：運算時間、記憶體、快取效益或 CI 成本的實測差異。
5. 驗證結果：通過、失敗、未執行與因來源缺失受阻的項目。
6. 剩餘瓶頸：目前的技術或科學限制，以及下一輪最有價值的改善方向。

每輪應額外列出新增、修改、合併、封存及移除的檔案及理由。

不以任務完成數量、檔案數量或測試數量作為唯一績效指標。

若本輪主要目標為工程重構，科學結果維持等價亦可視為必要且有價值的成果，但須以量測證明工程品質確實改善。

⸻

9. 技術債與例外治理

9.1 技術債

不得在已知的高複雜度函式中，無限制累積新條件與特殊案例。

當新增功能需改動高耦合模組時，優先評估：

* 拆分責任。
* 抽出共用函式。
* 使用標準化介面。
* 以組態或策略替代重複條件分支。
* 移除已被新實作取代的執行路徑。

允許將大型重構拆成多輪，不要求一次清除所有技術債。

9.2 例外處理

新方法具有明確研究價值，但暫時無法滿足工程或資料品質門檻時，可以保留在隔離實驗分支或影子資料層。

例外紀錄必須說明理由、受影響範圍、風險及後續驗證方法。

不得以形式上的驗收成功為理由，降低科學正確性、隱藏失敗或虛報研究增益。

⸻

最終開發判準

一項變更應依以下問題判斷其價值：

1. 是否增加實際可驗證的研究能力，或有效降低工程維護成本？
2. 是否保持科學資料及歷史結果的可追溯性？
3. 是否使架構更容易理解、測試、替換和擴充？
4. 是否避免新增不必要的重複邏輯、相依關係與歷史負擔？
5. 是否能以相同基準重播或量測變更帶來的結果？

研究能力、科學可靠性與長期可維護性，應共同構成 AU_REE_V3 的開發成功標準。
